# Tecnotron Pre-Alpha Normalization and Integral Development Cycle — Milestone Plan

## 1. Purpose

Complete the transition from the historical Tecnotron/FitFlow-ai development model to a coherent post-bootstrap Tecnotron baseline without rebuilding responsibilities already absorbed by the State Kernel, Operational Spine, or Self-Hosting Reconciliation.

This milestone is successful when Tecnotron has:

- one coherent active Source of Truth;
- historical material explicitly preserved, superseded, archived, or deferred without competing authority;
- canonical WP003 completed;
- a normal development cycle in which semantic work is concentrated before acceptance and post-acceptance mechanics are deterministic;
- a reusable independent-review specification so reviews are not authored from scratch;
- sufficient evidence that a real bounded Product task can traverse the complete cycle;
- a clean baseline from which later parallel development can begin.

This plan was first prepared externally and is materialized in the canonical repository under explicit Stage-B Developer authority. It defines the accepted current milestone sequence, but it does not authorize a later stage or repository effect by itself.

## 2. Development cycle target

The target cycle is already conceptually established and is not reopened by this milestone:

```text
SPEC / accepted Product responsibility
        ↓
PLAN
        ↓
TASK decomposition
        ↓
PHASE 1 — semantic
LLM / competent semantic actor
bounded authority + context + delta + tools
        ↓
frozen candidate
        ↓
INDEPENDENT REVIEW — semantic
clean bounded context using reusable review specification
        ↓
Developer acceptance
        ↓
PHASE 2A — deterministic
integrate + publish + verify
        ↓
PHASE 2B — deterministic
reconcile + satisfy obligations + close + fresh verify
```

Semantic escalation remains valid for missing, contradictory, ambiguous, illegal, or UNKNOWN effects. It is not part of the deterministic happy path.

## 3. Milestone boundaries

### Included

- historical repository and backlog reconciliation;
- normalization of active SOT/navigation and historical provenance;
- explicit disposition of historical responsibilities and technologies;
- completion of canonical WP003;
- investigation of the actual residual debt left by historical WP004/WP005 after bootstrap;
- creation of a new operational-maturation WP only if a real residual responsibility remains;
- reusable Independent Review specification/template and deterministic review-package mechanics where useful;
- maturation of deterministic Phase 2A / Phase 2B mechanics;
- bounded context/delta/tool/result contracts only to the degree required by the real development cycle;
- one integral real development-cycle proof before milestone closure.

### Explicitly deferred / out of scope

- semantic retrieval as a Product capability;
- MCP adoption;
- Temporal / orchestrator-workers / scheduler frameworks;
- Workflow Observer / fitness optimization;
- advanced telemetry or evaluation platforms;
- task-management framework development;
- GitHub Projects/Jira/provider selection for future task management;
- parallelization infrastructure itself;
- automatic multi-agent orchestration;
- permanent harness selection;
- optimization around OpenCode, Orca, Codex, ChatGPT Work, other LLM harnesses, or a particular model/provider;
- free-model benchmarking and context-size optimization as a milestone responsibility;
- advanced FinOps/ranking work.

These subjects may be revisited only after the integral cycle and SOT are stable enough to produce useful empirical evidence.

## 4. Governing principles

1. Do not rebuild responsibilities already satisfied by the bootstrap substrate.
2. Preserve Product semantics separately from execution-surface choices.
3. Historical artifacts remain provenance unless deliberately re-adopted by competent authority.
4. WP003 remains canonical and is not replaced by this reconciliation.
5. Historical WP004 Governed Task Cycle Lite is presumed superseded by the post-bootstrap vertical cycle unless a concrete residual normative responsibility is demonstrated.
6. Historical WP005/Observer concepts do not create current implementation debt merely by existing; only demonstrated residual needs survive.
7. A Plan should normally decompose into bounded Tasks with assigned SPEC requirements; WP003 will formalize and validate that relationship.
8. The current external pre-alpha reconciliation is an exception to normal repository task materialization because the repository's historical authority/navigation is itself being normalized.
9. Once normalized development begins, remotely visible/versioned Product artifacts are expected because future parallel actors need shared authority and state.
10. Do not design a Task-management framework when mature external providers can own planning views, queues, assignment, and dashboards later.

## 5. Stage A — Historical reconciliation and target SOT

### Mode

External semantic work. No canonical repository mutation.

### Objective

Produce one complete reconciliation of the remaining historical repository material so later stages no longer need to reconstruct architecture or authority from stale documentation, archived backlog, old runtime choices, or chat history.

### Required analysis

- active-but-stale documentation;
- archive/superseded material;
- historical backlog and roadmap items;
- historical TASK/lifecycle documentation;
- historical execution surfaces and technology choices;
- bootstrap responsibilities and remaining operational debt;
- current canonical WP responsibilities;
- current SOT/navigation structure.

### Required dispositions

Each relevant item receives one explicit disposition such as:

```text
PRESERVE_CANONICAL
SUPERSEDED_BY_BOOTSTRAP
SUPERSEDED_BY_NEWER_AUTHORITY
MAP_TO_WP003
CANDIDATE_OPERATIONAL_MATURATION_DEBT
DEFERRED_RESEARCH
ARCHIVE_PROVENANCE
REMOVE_FROM_ACTIVE_SOT
INSUFFICIENT_EVIDENCE
```

### Mandatory current dispositions to preserve unless new evidence contradicts them

- WP003: canonical and still required.
- Historical WP004 Task Cycle Lite: do not resume mechanically; bootstrap has absorbed its principal vertical-cycle purpose.
- Historical WP005 observation/fitness direction: do not resume mechanically; investigate only for a demonstrable residual responsibility later.
- Semantic retrieval, MCP, Temporal/orchestrator-workers: deferred.
- Orca/OpenCode/Codex/Work/other harness optimization: deferred until cycle + SOT stabilization.
- Workflow Observer / fitness: deferred until there is a stable product/process worth observing and optimizing.

### Outputs

- historical responsibility inventory;
- technology/research disposition matrix;
- predecessor milestone/WP disposition proposal;
- target layered SOT/navigation model;
- exact proposed canonical normalization delta;
- list of unresolved questions that genuinely block materialization.

### Exit gate A

Developer review confirms that:

- no material historical responsibility remains unclassified without an explicit reason;
- no duplicate responsibility is knowingly carried into the target roadmap;
- the target SOT model is coherent enough to materialize;
- the exact repository normalization delta is bounded;
- repository mutation is still NONE until separately authorized.

## 6. Stage B — Canonical repository normalization

### Mode

Normal Product repository change, only after explicit Developer authorization.

### Objective

Materialize the accepted Stage-A reconciliation so the canonical repository becomes a reliable active SOT instead of a mixture of current authority and historical residue.

### Scope

Only the accepted normalization delta, for example:

- SOT/navigation updates;
- roadmap/milestone reconciliation;
- explicit supersession/archive markers;
- removal of obsolete historical material from active navigation;
- preservation of provenance where valuable;
- documentation required to describe the post-bootstrap architecture accurately.

No unrelated feature implementation is authorized by this stage.

### Cycle

This repository-changing stage itself follows the current governed cycle:

```text
Phase 1 semantic repository change
→ frozen candidate
→ independent review
→ Developer acceptance
→ deterministic integration/publication where available
→ deterministic reconciliation/closure where available
```

Any remaining manual bootstrap mechanics are evidence for Stage D; they are not a reason to expand Stage B.

### Exit gate B

- active SOT is coherent and navigable;
- historical material cannot accidentally compete as current authority;
- roadmap/milestone status reflects the accepted post-bootstrap disposition;
- canonical repo is ready for normal Product development;
- no known cleanup responsibility is silently deferred into WP003.

## 7. Stage C — Complete canonical WP003 SDD

### Objective

Complete the already-canonical SDD Authority and Artifacts responsibility so Product intent, planning, task assignment, local execution strategy, evidence, review, and Developer acceptance have mechanically distinguishable relations.

### Expected continuation

Preserve the accepted WP003 decomposition unless competent evidence requires a formal change:

```text
WU01 — deterministic parser / relation validator
WU02 — templates / fixture corpus
WU03 — fail-closed lint / validation
WU04 — adoption/conformance disposition after WU01–WU03
```

WP003 does not become a second lifecycle State Machine. Its responsibility is to define and validate artifact semantics, authority, and relations.

### Normal-development implication

From this point forward, a sufficiently large PLAN is expected to decompose into bounded Tasks. Each Task receives explicit responsibility and assigned SPEC/RF scope instead of inheriting an entire milestone context.

This decomposition is a normal engineering practice and must not depend on a particular harness or model limitation.

### Exit gate C

- WP003 functional requirements are satisfied or explicitly dispositioned;
- SPEC → WP PLAN → TASK → task PLAN → RESULT → REVIEW relations are deterministically validatable;
- positive and negative fixtures demonstrate fail-closed behavior;
- WU04 has a competent disposition;
- future Product work can create bounded Tasks without inventing authority in prompts/chats/harness configuration.

## 8. Stage D — Post-bootstrap operational cycle maturation

### Entry condition

Stage B complete and WP003 complete.

### Objective

Determine the actual remaining operational debt after bootstrap + SOT normalization + SDD completion, then materialize only the minimum responsibility required to make the normal cycle reliable.

Historical WP004/WP005 are evidence inputs, not executable authority. If a real residual responsibility exists, define a new post-bootstrap WP with its own SPEC and PLAN instead of reviving the historical implementations.

### Candidate residual concerns

Only if demonstrated necessary by current cycles:

- reusable Independent Review specification/template;
- deterministic rendering/materialization of bounded review requests/packages;
- deterministic recording of independent-review results;
- hardening/composition of Phase 2A integration/publication/verification recipes;
- hardening/composition of Phase 2B reconciliation/satisfy/closure/verification recipes;
- bounded context contract;
- bounded delta/ownership contract;
- tool/capability allowlist contract;
- result/evidence contract;
- explicit semantic escalation for exceptional/UNKNOWN states.

### Explicit non-goals

- observer dashboards;
- fitness optimization;
- generalized workflow engine;
- scheduler;
- multi-agent framework;
- task-management provider;
- harness automation strategy;
- model benchmarking.

### Exit gate D

On the normal happy path:

```text
Phase 1 = semantic
Independent Review = semantic
Developer acceptance = human authority
Phase 2A = deterministic
Phase 2B = deterministic
```

No post-acceptance semantic actor is required unless deterministic execution reports an explicitly exceptional state.

## 9. Stage E — Integral real-cycle proof and milestone closure

### Objective

Prove the normalized system on real bounded Product work rather than by adding another synthetic framework layer.

### Proof cycle

Select one appropriately bounded real responsibility and execute:

```text
accepted Product SPEC/responsibility
→ PLAN
→ bounded TASK derived under WP003
→ Phase 1 semantic implementation
→ deterministic validation
→ frozen candidate
→ reusable independent semantic review
→ Developer acceptance
→ deterministic Phase 2A
→ deterministic Phase 2B
→ fresh authoritative state/evidence
```

Repeat only when the first real cycle exposes concrete unresolved debt. Do not turn repetition into an automation program during this milestone.

### Terminal milestone condition

The milestone can close when:

- the canonical repository exposes a coherent current SOT;
- historical authority is properly superseded/archived/deferred;
- WP003 is complete;
- the integral development cycle has been demonstrated on real bounded work;
- Phase 2A and Phase 2B are deterministic on the normal path;
- independent review can be instantiated from a reusable specification instead of authored from scratch;
- a new developer/LLM actor can receive bounded Task authority/context without reconstructing historical chats;
- the system is ready to consider parallel development as the next concern.

The milestone does NOT require actual parallelization, task-management provider adoption, or harness/model optimization.

## 10. Successor concerns after this milestone

Only after terminal closure should Tecnotron evaluate, based on real cycle evidence:

- parallel Product development;
- GitHub Projects / Issues / Jira or another task-management provider;
- remote coordination conventions;
- OpenCode/Codex/Work/other harness automation;
- free/included/local model suitability for bounded Tasks;
- context-budget optimization;
- semantic retrieval/MCP if evidence shows a real need;
- further orchestration/automation.

These are successor decisions, not hidden acceptance criteria for this milestone.

## 11. Stage-closure review protocol

This canonical milestone plan is the checkpoint document for every stage closure.

At the end of each stage:

1. Re-read the current canonical repository version of this plan.
2. Compare actual evidence/results against that stage's objective, outputs, and exit gate.
3. Record a stage disposition: `PASS`, `REVISE`, or `BLOCKED`.
4. Record concrete deltas and new evidence separately from the plan.
5. Do not rewrite the plan merely to make actual execution appear conformant.
6. Revise/version the plan only when the milestone scope, stage structure, or terminal condition genuinely changes and the Developer accepts that change.
7. A stage `PASS` does not automatically authorize the next repository effect; explicit authority boundaries remain applicable.
