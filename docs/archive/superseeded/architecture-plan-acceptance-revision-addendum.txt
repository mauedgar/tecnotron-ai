## D. Namespace and lifecycle ruling

### Namespace

La convención real vigente es:

```text
<namespace>-<artifact>/v<integer>
```

Todos los contratos existentes usan `fitflow-*`; no se encontró ningún schema `tecnotron-*`. Los candidatos aprobados respetan la forma existente y establecen el namespace nuevo:

```text
tecnotron-agent-profile/v1
tecnotron-agent-launch/v1
tecnotron-task-lifecycle/v1
tecnotron-execution-observation/v1
```

Estos son los IDs planificados finales para los contratos nuevos.

Reglas consolidadas:

- los contratos `fitflow-*` existentes permanecen inmutables;
- los contratos nuevos usan `tecnotron-*`;
- no se cambia el significado de una versión publicada;
- compatibilidad y migración son explícitas;
- la retirada de compatibilidad requiere otro ruling.

### WP-004 revisado

WP-004 ya no crea un sidecar permanente. Su resultado pasa a ser:

> `tecnotron-task-lifecycle/v1` es la única política operativa vigente al cierre, mientras `fitflow-task/v2` permanece como formato histórico aceptado únicamente a través de un boundary de compatibilidad.

#### Secuencia de migración

1. Definir `tecnotron-task-lifecycle/v1`.
2. Definir mapping explícito desde `fitflow-task/v2`.
3. Validar casos compatibles, ambiguos y rechazados.
4. Migrar consumidores Tecnotron-ai.
5. Migrar consumidores FitFlow mediante TASK separada cuando corresponda.
6. Documentar deprecación.
7. Retirar el uso operativo directo de la política antigua.
8. Mantener el parser/adapter compatible hasta otro ruling.

#### TASKs WP-004 revisadas

```text
TOF-W2-002 — Canonical Tecnotron Task Lifecycle Contract
```

- Crea contrato, mapping y tests.
- No modifica `fitflow-task/v2`.
- Reviewer obligatorio por schema/lifecycle.

```text
TOF-W2-003 — Tecnotron Lifecycle Consumer Migration
```

- Migra consumidores Tecnotron-ai al nuevo lifecycle.
- Mantiene el adapter de compatibilidad en el boundary.
- Prueba que validación, review, aceptación e integración permanecen ortogonales.

```text
TOF-W2-004 — FitFlow Lifecycle Consumer Migration
```

- Condicional al inventario WP-000.
- TASK FitFlow independiente con baseline, branch, worktree y allowlist propios.
- Reviewer obligatorio.
- Si no hay consumidores reales, se cancela con evidencia y no se inventa trabajo.

#### Gate adicional WP-004

Al cierre debe cumplirse:

```text
new canonical policy: tecnotron-task-lifecycle/v1
legacy input compatibility: fitflow-task/v2
operational policy count: 1
direct legacy-policy consumers: 0
```

La formulación anterior “nueve adapters OpenCode” queda supersedida.

### Resultado aprobado

```text
un launcher genérico parametrizado por perfil
+ nueve perfiles project-scoped
+ tecnotron-agent-launch/v1
+ smokes positivos y negativos
```

### Perfiles

| Perfil | Escritura efectiva |
|---|---|
| `spec_analyst` | ninguna |
| `planner` | ninguna |
| `architect` | ninguna |
| `explorer` | ninguna |
| `implementer` | código y tests sólo bajo TASK |
| `doc_curator` | documentación sólo bajo TASK |
| `reviewer` | ninguna |
| `researcher` | ninguna; web sólo bajo TASK autorizada |
| `auditor` | ninguna |

La escritura de planes o SPEC por perfiles read-only se devuelve como output propuesto hasta que una TASK posterior autorice explícitamente un writer. No se infiere permiso de escritura de la responsabilidad semántica.

### Launcher genérico

Input conceptual:

```yaml
profile_id:
task_path:
worktree_root:
model_requested: null
reasoning_effort: null
context_pack_ref: null
environment:
  FF_PROJECT_ROOT:
  FF_PROJECT_PROFILE:
  FF_AI_CORE_ROOT:
```

Responsabilidades:

- resolver uno de los nueve perfiles;
- validar TASK, cwd y worktree;
- aplicar deny-by-default;
- inyectar environment task-scoped;
- invocar `opencode run` mediante un único adapter;
- no modificar configuración global;
- normalizar resultado contra `tecnotron-agent-launch/v1`.

### Smokes

**Positivos**

- discovery de nueve perfiles;
- lanzamiento acotado de perfil read-only;
- implementer dentro de ownership;
- doc_curator dentro de docs;
- ejecución sin modelo explícito cuando OpenCode lo admita;
- modelo solicitado registrado separadamente.

**Negativos**

- perfil `coder_*`;
- segundo implementer;
- delegación;
- web fuera de researcher;
- escritura read-only;
- escritura implementer/doc_curator fuera de ownership;
- cwd/worktree incorrectos;
- profile/model binding permanente;
- salida CLI malformada;
- configuración/global profile mutation.

## F. Evidence and SPEC approval model

### Evidencia estructurada aprobada

```text
TASK + Run Store + RESULT + evidencia final sanitizada
```

| Artefacto | Responsabilidad |
|---|---|
| `TASK.md` | contrato de ejecución y RF asignados |
| Run Store | eventos y observación operativa |
| `RESULT.md` | resumen legible, divergencias y referencias |
| Artifact sanitizado | snapshot verificable del run final relevante |

El artifact no replica el event log completo.

Contenido mínimo:

```yaml
schema_version: tecnotron-execution-observation/v1
run_id:
usage_record_id:
content_hash:
model_requested:
model_resolved:
provider:
reasoning_effort:
usage:
  source: provider | estimated | unavailable
  input_tokens: null
  output_tokens: null
  cached_tokens: null
  total_tokens: null
validator_result: PASS | FAIL | UNAVAILABLE | NOT_RUN
reviewer_result: PASS | FAIL | UNAVAILABLE | NOT_RUN
execution_disposition:
```

Reglas:

- `usage_record_id` enlaza RunEvent y artifact.
- `content_hash` verifica el snapshot.
- Developer acceptance e integration no forman parte mutable de la observación.
- RESULT referencia el artifact y sus hashes.
- La observación original no se reescribe tras aceptación.
- No se duplica el event log ni Run State.

### SPEC approval checklist del Milestone Plan

```markdown
- [ ] WP-001 SPEC aprobada por Developer
- [ ] WP-002 SPEC aprobada por Developer
- [ ] WP-003 SPEC aprobada por Developer
- [ ] WP-004 SPEC aprobada por Developer
- [ ] WP-005 SPEC aprobada por Developer
- [ ] WP-006 SPEC aprobada por Developer
```

- WP-000 no requiere SPEC mientras materialice contratos existentes.
- WP-007 no requiere SPEC mientras sólo ejecute cierre y promoción.
- Los RF candidatos son base de clarificación.
- Los RF no llevan checkboxes de ejecución.
- Cobertura RF se registra en RESULT o en una matriz derivada.
