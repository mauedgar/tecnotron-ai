### Hallazgos contractuales relevantes

- `RunEvent` ya reserva `usage_record_id` y exige Developer para emitir `DONE`.
- `RuntimeIdentity` separa propuesta y runtime efectivo.
- `ContextPackager` distingue tokenizer exacto de estimación.
- `RunState` ya conserva context deliveries, route, validation/review refs y retries.
- `Task.status` mezcla estados de planificación/ejecución y no representa por sí solo aceptación, integración ni doc sync.
- `ProjectProfile` y `resolveProject` siguen nombrando FitFlow y `FF_PROJECT_*`. Cambiarlos sin ruling puede romper consumidores externos.
- El Router sólo acepta roles `actor_type: model`; esto no debe usarse como definición de los nuevos perfiles operativos.
- Los perfiles históricos incluían modelos y, en algunos casos, web. Eso contradice las decisiones nuevas.

## D. Canonical authority model

No se establece una precedencia lineal universal. La autoridad se resuelve por responsabilidad:

| Responsabilidad | Autoridad |
|---|---|
| Invariantes, estados válidos, schemas, interoperabilidad | Contratos y ADR canónicos |
| Comportamiento esperado de una capacidad | `SPEC.md` aprobada |
| Solución técnica y división del WP | WP `PLAN.md` |
| Autorización operativa y RF asignados | `TASK.md` |
| Estrategia local | Task `PLAN.md` |
| Evidencia observada | `RESULT.md`, Run Store y artifacts |
| Revisión semántica | `REVIEW.md` |
| Aceptación | Developer |
| Secuencia macro | Roadmap |
| Realidad implementada confirmada | Current State |
| Navegación | Source of Truth |
| Explicación operativa | Guides, siempre derivadas |
| Hipótesis | Research |
| Historia | Archive/tag |

### Resolución de conflictos

1. Identificar qué responsabilidad está en conflicto.
2. Si una SPEC contradice un contrato o ADR, detener y pedir ruling.
3. Si PLAN o TASK cambia comportamiento, actualizar y aprobar primero la SPEC.
4. Si Task PLAN amplía TASK, detener.
5. Si RESULT contradice la expectativa, conservar la evidencia y no reescribirla.
6. Si una guía contradice una fuente canónica, corregir o superseder la guía.
7. Ningún índice, runtime o provider resuelve conflictos de autoridad.

## E. Documentation architecture

### Estructura objetivo progresiva

```text
docs/
├── SOURCE_OF_TRUTH.md
├── current-state.md
├── implementation-roadmap.md
├── compatibility-baseline.md
├── architecture/
├── decisions/
├── guides/
├── milestones/
├── work-packages/
├── tasks/
├── research/
└── archive/
```

No deben crearse directorios hasta que una task cree contenido real.

### Clasificación

- **Canonical:** contratos, ADR, SPEC aprobadas, arquitectura, lifecycle y estado.
- **Guide:** explicación no normativa.
- **Research:** observaciones e hipótesis.
- **Archive:** referencias históricas excluidas del contexto cotidiano.
- **Derived:** ledger, índices semánticos y packages regenerables.

### Metadata mínima

```yaml
document_id:
type:
status: draft | proposed | approved | canonical | superseded | research | archived | derived
owner:
updated:
milestone:
work_package:
spec:
requirements: []
tasks: []
supersedes: []
```

Usar links Markdown relativos. Los wikilinks pueden mantenerse transitoriamente, pero no deben ser el único mecanismo de navegación.

### Principio de movimientos

Los seis movimientos históricos coinciden con el layout solicitado y pueden reutilizarse como propuesta de paths, no como decisión heredada. Deben ejecutarse bajo una task mecánica separada, con validación de todos los enlaces.

TASK/PLAN/RESULT/REVIEW aceptados de 008/009 permanecen en sus paths estables.

## F. Milestone Plan

```yaml
id: TOF-V1
name: Tecnotron Operational Foundation v1
slug: tecnotron-operational-foundation-v1
status: PROPOSED
milestone_baseline: 41088a413d06ed1d58d63d92320e38d4b44b86ea
integration_target: tools
promotion_target: main
```

### Objetivo

Establecer un flujo vertical sostenible que permita especificar una capacidad, derivar tasks, ejecutar un perfil mediante OpenCode, validar, revisar según riesgo, obtener aceptación del Developer, integrar por squash en `tools` y conservar evidencia mínima útil.

### Resultado terminal

Al menos una capacidad representativa completa:

```text
SPEC aprobada
→ WP PLAN
→ TASK/PLAN
→ worktree feat/*
→ perfil operativo
→ launcher OpenCode
→ contexto acotado
→ evidencia de runtime
→ Validator
→ Reviewer según riesgo
→ Developer gate
→ squash a tools
→ trazabilidad documental
```

El milestone queda documentado y listo para promoción deliberada a `main`.

### Límites

**Incluye**

- perfiles operativos;
- launchers deterministas;
- SDD;
- Task Lifecycle Lite;
- evidencia mínima;
- guía y navegación;
- cierre y promoción.

**Excluye**

- ranking de modelos;
- bindings permanentes;
- selección basada en fitness;
- provider research;
- FinOps avanzado;
- telemetría extensa;
- Temporal, MCP y retrieval nuevos;
- modificación de FitFlow;
- recuperación automática del milestone archivado.

### Waves y WPs

| Wave | WP | Capacidad |
|---|---|---|
| W1 | WP-001 | Operational Profile Contracts |
| W1 | WP-002 | Deterministic OpenCode Launchers |
| W2 | WP-003 | SDD Authority and Artifacts |
| W2 | WP-004 | Governed Task Cycle Lite |
| W3 | WP-005 | Execution Observation Baseline |
| W4 | WP-006 | System Guide and Navigation |
| W4 | WP-007 | Milestone Closure and Promotion |

W4 se divide en dos WPs porque guía y cierre tienen resultado, ownership y gate distintos.

### Gates

- **G0:** Developer resuelve namespace/compatibilidad FitFlow–Tecnotron.
- **G1:** SPEC y contrato de perfiles aprobados.
- **G2:** perfiles y launcher pasan smokes positivos/negativos.
- **G3:** SDD y dimensiones lifecycle aceptadas.
- **G4:** ciclo manual vertical completado sobre una task real.
- **G5:** observation contract enlazado sin duplicar estados.
- **G6:** System Guide y navegación validados.
- **G7:** todos los WPs aceptados e integrados; promoción autorizada.

### Cierre y promoción

`tools -> main` sólo si:

- todos los WPs están cerrados;
- no hay RF sin disposición;
- Validator pasa;
- reviews requeridos están completos;
- aceptación Developer está registrada;
- integración de cada task es verificable;
- documentación y links están sincronizados;
- no hay cambios FitFlow ni artefactos históricos recuperados;
- el diff de milestone está libre de cambios no declarados.

## H. SPEC plans

### WP-001 SPEC — Operational Profiles

**Actores:** Developer, perfiles operativos, Validator.

**Casos de uso:** seleccionar responsabilidad; limitar permisos; rechazar perfil retirado.

**RF candidatos**

- **RF-001:** el sistema debe reconocer exactamente `spec_analyst`, `planner`, `architect`, `explorer`, `implementer`, `doc_curator`, `reviewer`, `researcher` y `auditor`.
- **RF-002:** sólo `implementer` puede escribir source y siempre bajo ownership de TASK.
- **RF-003:** ningún perfil debe incorporar provider o modelo a su identidad.
- **RF-004:** delegación debe estar denegada para todos.
- **RF-005:** web debe estar denegada salvo para `researcher`.
- **RF-006:** perfiles personales del Developer deben permanecer fuera del registry canónico.

**RNF-001:** deny-by-default.  
**RNF-002:** definición portable y validable sin ejecutar un modelo.

**Edge cases:** ID histórico, perfil duplicado, write scope vacío, researcher sin research task.

**Out:** Router, Model Resolver, fallback y ranking.

**Completion:** schema + set exacto + pruebas negativas + aprobación Developer.

**Pregunta abierta:** namespace del schema (`tecnotron-*` o compatibilidad `fitflow-*`).

**Workload:** specification/high/high/fit/medium/medium.

### WP-002 SPEC — Launchers

- **RF-101:** el launcher debe recibir perfil, task/worktree y parámetros de ejecución explícitos.
- **RF-102:** debe validar perfil, cwd, ownership y permisos antes de invocar OpenCode.
- **RF-103:** un `model_hint` puede influir en la solicitud, pero no modifica el perfil.
- **RF-104:** debe distinguir modelo solicitado, resuelto y observado.
- **RF-105:** debe producir un envelope normalizado con status, exit code, artifacts y runtime identity.
- **RF-106:** debe fallar cerrado ante CLI no disponible, salida inválida, permiso denegado o perfil retirado.

**RNF:** determinismo, Windows/CI, stdout estructurado, stderr diagnóstico.

**Edge:** ausencia de modelo, timeout, salida parcial, OpenCode cambia flags.

**Pregunta:** formato real soportado por la versión local de `opencode run`.

**Workload:** specification/high/high/fit/high/large.

## J. Task Lifecycle and tool boundaries

| Componente | Responsabilidad | No posee |
|---|---|---|
| Developer | SPEC, estrategia, rulings, aceptación y promoción | ejecución mecánica |
| Orca | workspace, sesión, terminal y presentación | autoridad, aceptación, routing |
| OpenCode | ejecutar perfil/modelo | Git lifecycle, source of truth |
| Router | derivar rol ejecutable y requirements desde policy | perfil manual, modelo, ejecución |
| Model Resolver | propuesta provider/runtime elegible | ejecución o identidad efectiva |
| ContextPackager | retrieval, budget, coverage, fallback metadata | suficiencia final |
| Explorer | localizar/evaluar evidencia según contrato | materialización, aceptación |
| Agent Runtime | ejecutar adapter y observar identidad | rerouting, aceptación |
| Validator | schema, tests, diff, ownership y RF | review o aceptación |
| Reviewer | revisión semántica según riesgo | fixes, integración, aceptación |
| Run Store | eventos/artifacts/proyección | política o verdad documental |
| GitHub Projects | coordinación y estado provider | canonical TASK/SPEC |
| Task Lifecycle | branch, worktree, transiciones e integración | implementación semántica |

### Reconciliación de estados

No se debe ampliar directamente `State` con estados administrativos. Mantener:

1. **Workflow state:** routing, exploring, executing, validating, reviewing.
2. **Validation result:** PASS/FAIL/UNAVAILABLE/NOT_RUN.
3. **Review decision:** semantic verdict o NOT_RUN justificado.
4. **Developer acceptance:** pending/accepted/rejected.
5. **Integration:** target/SHA/status.
6. **Lifecycle bookkeeping:** discovered→ready→…→done→cleanup.

El contrato nuevo debe ser aditivo y no reinterpretar `fitflow-task/v2`.

## K. Model evidence plan

### Campos existentes reutilizables

| Evidencia | Fuente existente |
|---|---|
| `run_id`, `task_id` | RunEvent/RunState |
| rol propuesto | RouteDecision/RunEvent actor |
| modelo resuelto/provider | ModelResolutionResult |
| modelo observado | RuntimeIdentity.effective |
| context pack/tokens | ContextPackagerResult y ContextDelivery |
| retries | RunState.retry_counters |
| Validator/Reviewer refs | RunState histories |
| aceptación | `DEVELOPER_DECISION` RunEvent |
| correlación | `RunEvent.usage_record_id` |

### Campos nuevos mínimos

- model requested y reasoning effort;
- provider usage tokens y `usage_source`;
- latency;
- context expansions;
- instruction violations;
- unsupported claims;
- reusable output;
- Developer interventions/rework;
- first-pass acceptance;
- final execution disposition.

### Ubicación recomendada

- Raw/derived runtime evidence: Run Store con root explícitamente inyectado.
- Registro sanitizado candidato:  
  `docs/tasks/<task-id>/evidence/<usage-record-id>.json`
- `RESULT.md`: resumen y hash/ref, no copia completa.

No crear el directorio `evidence/` si la task no produce un registro.

### Inmutabilidad y estados

El observation record se finaliza una vez antes del acceptance gate. La aceptación y la integración posteriores se conservan en sus eventos/lifecycle records; no se reescribe retrospectivamente la observación.

`final_disposition` debe describir el resultado de la ejecución, no sustituir `developer_acceptance` ni `integration`.

### Medición versus estimación

- `usage_source: provider`: sólo si el runtime entrega cifras.
- `estimated`: exige algoritmo y limitación.
- `unavailable`: valores de tokens `null`.
- Los tokens de ContextPackager no deben presentarse como usage del provider.
